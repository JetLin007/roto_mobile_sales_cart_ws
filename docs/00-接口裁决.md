## B. 仍需裁决的 5 处（已按下列结论落地，你若反对我改）

### D1 `local/cart/status` 的 QoS：取 1
- 协议 v1.3 §1.2 表：QoS 1。
- 架构 v1.2 §5.2 正文：“除运动速度和屏幕心跳 QoS0 外，其余 QoS1”，但其表格该行写 0 —— **v1.2 自身前后矛盾**。
- 裁决：按 v1.3 与 v1.2 正文，`local/cart/status` = QoS1；`local/ui/heartbeat` = QoS0。配置项 `mqtt.local.cart_status_qos / heartbeat_qos` 可改。

### D2 OFFLINE 的表达：枚举值，不用布尔字段
- v1.2 §6.6 把 `OFFLINE` 列为第 8 状态；v1.3 §2.2.13 Schema 里 `OFFLINE` 只出现在 LWT 的 `oneOf` 分支。
- 裁决：`CartState.system_state` 增加 `STATE_OFFLINE=7`，删除上一版草案的 `bool offline`（避免“状态与标志位”双真相）。
- 序列化硬规则：`system_state==STATE_OFFLINE` 时**只**发 `{msg_id,timestamp,cart_id,system_state}` 四个键，其余字段不填；正常遥测报文出现 `OFFLINE` 视为非法，`service_cloud_comm` 直接丢弃并记 `INTERNAL_ERROR`。

### D3 时间基准：云端四时间戳为主，GNSS 降为可选
- v1.1 P10 / §4.2 写“GNSS 授时为最高优先级时源 + driver_gps 提供 PPS”。
- v1.2 P10 改为“四时间戳算法与云端对时”，§4.2 写“GNSS 授时**或**云端四时间戳对时”，`driver_gps` 不再提供 PPS。
- 裁决：`time.sync_mode=cloud_four_timestamp` 为主时源（周期 6h + 每次重连），GNSS 存在时仅作独立校验源（`gnss.enabled=false`，硬件到位再开）；`chrony` 作为唯一收敛出口，`offset>50ms` 时先校时再接新动作（v1.3 §2.2.7）。
- 影响：`TimeSyncRequest/Response` 保留 `t1..t4`；`driver_gps` 职责降为只发 `/gps/fix`，不碰时钟。

### D4 远控三个时间参数：200ms / 10Hz / 500ms
- v1.2 §6.9：`expire_at` 极短窗口（如 200ms），云端 10Hz 发帧，500ms 无有效包本地刹停。
- v1.3 §2.2.4 只给 500ms，未给帧窗口。
- 裁决：三参数全部进 `config.remote`：`frame_expire_window_ms=200`、`motion_rate_hz=10`、`stop_timeout_ms=500`；远控准入黑名单 `MAKING/ORDERING/OTA/FAULT/CHARGING`（v1.3 §2.2.4 “制作、开门、待取或充电时禁止普通移车”，v1.2 §6.9 “非 MAKING、非 CHARGING”）。
- 注意：`CHARGING` 不是状态机状态，由 `BatteryStatus.is_charging` 派生，作为独立互锁条件，不进 `system_state` 枚举。

### D5 错误码：并集 14 个，不做子集
v1.2 §10.1 的 10 个 + v1.3 §4.7 的 `PICKUP_UNVERIFIED / RFID_UNSTABLE / DOOR_OPEN_TIMEOUT / QUERY_UNAVAILABLE`。前者是“车端必须遵守”的核心集，后者是柜体/查询专用集，同属 `error_code` 字符串空间，合并后由 `ErrorCode.msg` 常量统一管理。
“是否可重试 / 是否未执行”不写进常量（v1.3 §2.2.11 明确 `unexecuted` 不能由错误码固定赋值），由业务层按执行记录判定。

## B2 构建与代码结构裁决（2026-11-16 修订：双轨构建）

> 前一版曾裁决“取消 buildx 交叉构建、只做板端原生编译”（DEV-01）。该结论已作废：
> 架构 §8.1 的 buildx 交叉构建**保留**，另加板端 git 原生验证通道。

### D8 双轨构建：WSL2 buildx 交叉 + 板端 git 原生验证
- **轨道 A（开发/出镜像）**：WSL2 `docker buildx --platform linux/arm64`；默认 push 私有 Registry，离线走 `--output type=oci` 落 tar，板端 `skopeo copy oci:... docker-archive:...` 后 `docker load`。
- **轨道 B（发布验证）**：RK3576S 上 `git fetch && checkout <tag>` → `scripts/build_on_board.sh --pull --require-clean` 在 `roto-build:arm64` 容器内原生 `colcon build` → 起容器跑联调。
- 一致性凭据：镜像 OCI label `org.opencontainers.image.revision=git_rev`；板端 `install/BUILD_INFO.txt` 记 `git_rev/git_desc/uncommitted/jobs/mode/arch`。**两者 `git_rev` 相同且 `uncommitted=0` 才算发布通过**。
- 为什么两条都要：buildx 验证“镜像可构建”，板端原生编译验证“aarch64 上真能编过、真能跑”，两者失败原因不同（前者多为 Dockerfile/依赖层，后者多为 GCC/内核/温度降频）。

### D9 板端代码更新只走 git，不走 rsync
- 发布验证路径固定：`git clone`（首次）→ `git fetch --all --tags` → `git checkout <tag>`；`--ff-only` 拉取，禁止 merge commit 污染。
- `scripts/sync_to_board.sh` 降级为**调试专用**（快速试错、改一行看一眼），不参与发布，也不写发布目录。
- 分支：`main` 可发布；`feat/*` 允许在板上试编；发布前必须打 tag（如 `v1.3.0-rc1`）。
- 板端认证用 deploy key（只读），不存用户名密码。

### D10 镜像 tag 规则
- 发布：多架构 manifest `roto-cart:1.3.0`（amd64+arm64），板端 `docker pull` 自动选 arm64。
- 调试：单架构必须带后缀 `roto-cart:1.3.0-arm64`；**禁止无后缀的单架构 tag**（防止 WSL2 误拉 arm64 镜像）。
- 版本戳一律取 `git describe --tags --always --dirty`，dirty 状态禁止发布。

### D6 代码结构：`core/` 与 `node/` 双层拆分
WSL2 上即便有 ROS2，也不该把协议解析塞进 `rclcpp` 回调 —— 否则 amd64 单测覆盖不到真实逻辑。
- `include/<pkg>/core/` + `src/core/`：纯 C++17，只依赖标准库与第三方（libmodbus/libserial），**不 include `rclcpp`**；
- `src/node/`：ROS 壳，只做“消息 ↔ core 结构体”转换、参数加载、线程/定时器编排，**不写业务判断分支**。
- 收益：帧编解码、状态机、数量账本、仲裁逻辑在 WSL2 用 `g++ + gtest` 就能测；板端只编壳。
- CI 卡点：`grep -rn 'rclcpp\|ros2' src/*/src/core` 必须为空。

### N1 文档事实纠正：RK3576 的 CPU
架构 §9.4 写“4 核 A76/A55 混合”，那是 RK3588 口径；RK3576 实际为 **4×Cortex-A72 + 4×Cortex-A53**。
影响：CPU 70% 预算的测算基准、编译并行度都按 A72/A53 重算，`-j4` 起步。

### D11 路径约定：源码仓与运行时根分离
- **源码仓**：WSL2 `~/ws/roto_mobile_sales_cart_ws`、板端 `/data/workspace/roto_mobile_sales_cart_ws`，同名同构，`git clone` 即可；构建产物 `build/ install/ log/` 留在仓内并被 `.gitignore` 排除。
- **运行时根**：`/opt/roto_ws`（架构 §4.5/§8.2 M6 统一路径），只放宿主可变数据 `config/ log/ data/cart.db`。二进制不落宿主，随镜像 OTA。
- 挂载口径：容器 `-v /opt/roto_ws/config:/opt/roto_ws/config`（架构原文），另加 `-v /opt/roto_ws/log:...`、`-v /opt/roto_ws/data:...`（本项目补充，步骤 7 随 Dockerfile/compose 落地）。
- 反向约束：**禁止**把源码仓当运行时根（`data/cart.db`、`log/` 会与 `git pull` 争同一棵树，回滚镜像时易误删数据）；**禁止**在运行时根里 `git pull`。
- 脚本已按此实现：`build_on_board.sh --src <源码仓> --runtime <运行时根>`，`--deploy-config` 才把 `config/` 写进运行时根；`sync_to_board.sh` 目标是源码仓，不是 `/opt/roto_ws`。

### D13 契约落地裁决（基于存量仓库 6 msg / 0 srv 的实测清单，2026-11-17）

存量仓库实测：`robot_msgs` 只有 6 个 msg（Alarm / BmsStatus / ChassisCmd / ChassisState / GpsFix / OrderEvent），0 个 srv；命名为 `std_msgs/Header`，无 `ProtocolHeader`。

| # | 裁决 | 依据 |
|---|---|---|
| 1 | **底盘走 RS485**（不是 CAN）。`driver_can_chassis` 在 M3 阶段废弃，`driver_chassis_rs485` 承接；`CmdVel` 去掉 `gear` 档位，改 `enable + 有符号 linear_x` | 用户确认“底盘 485 通信” |
| 2 | `BatteryStatus` **扩展** `float32 current_a`、`uint8 health`（0xFF=未知） | 保留存量充电判定与电池健康度能力，避免删字段后业务逻辑无据 |
| 3 | **超声波走独立串口**。`ChassisStatus` 不含超声波字段，由 `driver_ultrasonic` 发 `sensor_msgs/Range` → `/ultrasonic/range` | 用户确认“独立串口” |
| 4 | `PAUSE / RESUME / ARRIVED` **裁掉**，不进 `OrderAction.action_type`；暂停由本地 UI 直接控底盘停车 | 用户确认“裁掉”；v1.2 契约无此枚举 |
| 5 | `CmdVel` **保留** `float32 linear_y`（麦轮横移，差速底盘恒 0） | 用户确认“保留” |

**字段口径变更（迁移时必须同步改代码，否则逻辑错但编译不报错）**：
- `BmsStatus.voltage` int16 **mV** → `BatteryStatus.voltage` float32 **V**（1000 倍）
- `BmsStatus.temp` int16 **0.1°C** → `BatteryStatus.temperature` float32 **°C**（10 倍）
- `BmsStatus.charging` → `is_charging`；`Alarm.cleared` bool → `AlarmEvent.status` 枚举
- `Alarm.level` 4 档(1/2/3/4) → 3 档(0/1/2)，FATAL 并入 CRITICAL
- `OrderEvent` 方向是**下行命令**，拆为 `OrderCommand` + `LocalOrderStart`；`payload_json` 废除，改 `OrderAction[]`；`TaskEvent/TaskAction` 是**全新上行通道**，存量仓库原本没有
- `GpsFix` 删除 → `/gps/fix` 用 `sensor_msgs/NavSatFix`；速度/卫星数/hdop/vdop 迁入 `GeoLocation`

**过渡策略**（不一次推倒）：
- M2-a：37 个新 msg + 9 srv + 存量 6 个旧 msg 共存，CMakeLists 用 `CMakeLists.transition.txt`（59 条目），验收 `ros2 interface list | grep -c robot_msgs` = **53**
- M2-b：逐包把引用切到新类型，每包一个 commit
- M2-c：`grep` 确认零引用后删 6 个旧 msg，换 `CMakeLists.final.txt`（53 条目）

## C. 契约层四条硬规矩

1. **NULL 表达**：字符串 null → `""`（`pickup_code`、`cabinet_id`、`cabinet_label`、`assigned_slot`、`transaction_id`、`error_code`、`stage`、`order_id`、`query_msg_id`）；整型 null → `-1`（`progress`、`estimated_remaining_sec`）。JSON 互转只在 L3 通信层做。
2. **时间**：统一 `int64 timestamp_ms`（UTC 毫秒），不用 `std_msgs/Header`；`ProtocolHeader` 同时携带 `msg_id`（幂等键）与 `protocol_version`（v1.3 兼容）。
3. **IDL 演进**：只追加不删除；跨主版本保留旧类型并标注弃用周期。
4. **标准消息优先**：能落到 ROS2 标准类型的不用自定义 —— `/chassis/odom` 用 `nav_msgs/Odometry`，`/scan` 用 `sensor_msgs/LaserScan`，`/ultrasonic/range` 用 `sensor_msgs/Range`，`/gps/fix` 用 `sensor_msgs/NavSatFix`，`/camera/image_raw` 用 `sensor_msgs/Image`。`robot_msgs` 只管协议与业务语义。
